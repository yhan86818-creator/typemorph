Implementing gRPC-Web from JSON: Bridging Web and Microservices

gRPC-Web allows web applications to communicate directly with gRPC backend services. Historically, web browsers couldn't speak the gRPC protocol (HTTP/2 with trailers). gRPC-Web provides a proxy-based or native solution to bridge this gap. Converting your existing JSON-based REST endpoints to gRPC-Web involve defining your schema in Protobuf and generating client-side stubs that can be called from TypeScript or JavaScript.

Live Example

JSON Request for a product details service:

// Request
{ "product_id": "p_99" }

// Response
{ "name": "Smart Watch", "price": 199.99 }

Corresponding gRPC-Web service definition (Proto):

service ProductService {
  rpc GetProduct(ProductRequest) returns (ProductResponse);
}

message ProductRequest {
  string product_id = 1;
}

message ProductResponse {
  string name = 1;
  float price = 2;
}

Implementation Guide

  1. Schema Definition: Convert your JSON inputs/outputs into Protobuf messages and define a service with rpc methods.
  2. Stub Generation: Use protoc-gen-grpc-web to generate JavaScript/TypeScript client code from your .proto file.
  3. Proxy Configuration: Set up an Envoy proxy or a gRPC-Web compatible gateway (like the one built into some Cloud Load Balancers) to translate between HTTP/1.1 (Web) and HTTP/2 (gRPC).
  4. Client Integration: Import the generated service client in your frontend and call methods like client.getProduct(request, metadata, (err, response) => { ... }).
  5. Metadata Handling: Replace your REST headers (like Authorization) with gRPC metadata.

Technical Deep Dive

gRPC-Web supports two modes: grpcwebtext (Base64 encoded) and grpcweb (Binary). While grpcweb is more efficient, grpcwebtext is more compatible with older browsers. Unlike REST, where you might use different HTTP verbs (GET, POST, PUT), gRPC-Web uses a single POST endpoint for all calls, with the method name encoded in the URL (e.g., /ProductService/GetProduct). This simplifies infrastructure routing while maintaining strict type safety from the server to the browser, eliminating the common "undefined is not a function" errors when API responses don't match frontend expectations.

Best Practices

  • Use TypeScript: The greatest benefit of gRPC-Web is the end-to-end type safety provided by generated TypeScript interfaces.
  • Error Mapping: Map your JSON error responses to standard gRPC status codes (e.g., NOT_FOUND, UNAUTHENTICATED).
  • Deadline Support: Leverage gRPC's built-in deadline (timeout) propagation to ensure web clients don't hang on slow backend services.

FAQ

Q: Can I use gRPC-Web without a proxy?
A: Currently, most backend servers require a proxy (like Envoy) to handle the HTTP/2 trailer translation, though some libraries (like connect-rpc) are making this easier.

Q: Does gRPC-Web support bi-directional streaming?
A: No, due to browser limitations, only Unary and Server-side streaming are currently supported in the gRPC-Web spec.
