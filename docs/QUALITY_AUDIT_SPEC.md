# Feature Spec: Output Quality Audit (Real Compiler Verification)

## 1. 背景・目的

TypeMorphには140+件のテストが存在するが、調査の結果、**実際のコンパイラ/型チェッカーで出力を検証しているのはTypeScriptとPythonの2言語のみ**であることが分かった(`src/lib/__tests__/compile-check.test.ts`)。

Go, Java, Swift, Kotlin, Rust, NestJS DTO, Effect Schema等、他のTier 1ジェネレータ(`src/lib/targets.ts`で`tier: 1`、つまり「十分にテストされた中核ジェネレータ」と位置づけられているもの)は、実際には以下の方法でしか検証されていない。

- 出力文字列に特定のキーワード(`struct`, `@Data`, `import Foundation`等)が含まれているかの正規表現マッチ
- 波括弧・丸括弧の数が対応しているかのカウント

これは「文法的に正しいかもしれない」ことしか保証せず、型の誤り・存在しないimport・意味的な誤生成(例: 過去に見つかった「SQLのnullable defaultが反転している」「union型がanyに収束する」「TypeScriptパーサーでregexが途中で切れる」等)を検出できない。**「Tier 1=十分にテストされた」という製品内部の前提と、実際の検証の厳密さに食い違いがある。**

この機能の目的は、新機能の追加より先に、**Tier 1の全ジェネレータに対して、実際の言語処理系(コンパイラ・インタプリタ・型チェッカー)による検証を追加すること**。新機能は一切スコープに含めない。

## 2. やりたいことの具体像

`src/lib/targets.ts`で`tier: 1`と定義されている全ターゲット(TypeScript, Zod, Go, Rust, Python, Java, C#, Swift, Kotlin, PHP, Dart, GraphQL, Protobuf, JSON Schema, SQL/Prisma)に対して、それぞれの言語の実処理系を使った検証を追加する。

既に実装済みの`compile-check.test.ts`内のTypeScript/Pythonのパターン(実際に`tsc --noEmit --strict`や`py_compile`を呼ぶ)を参考に、他の言語にも同様の「本物の検証」を拡張する。

検証に使う入力スキーマは、既存の`compile-check.test.ts`にある`ORDER_JSON`(ネスト・配列・null・enum・日付・UUIDを含む実務的なJSON)をベースに、過去に実際にバグが見つかった構造的パターン(union型、nullable/optionalの組み合わせ、再帰型、深いネスト)を追加でカバーすること。

- **Zod**: 既存の`compile-check.test.ts`内のZodテストは、「zodパッケージ本体が無いため型チェックを諦め、構文チェックと文字列マッチに後退している」という妥協がある(コード内のコメント参照)。`zod`はTier 1指定のターゲットであるため、`zod`パッケージを`devDependencies`に追加し、実際に`z.infer`等を含めた型チェックまで通すこと。`zod`パッケージは軽量(数百KB程度)であり、後述の「ローカルにインストールしない」制約の対象外とする。

以下は各言語に対して「文字列マッチではなく実処理系を使う」ことの参考イメージ。具体的なコマンド・セットアップ方法は実装者が判断すること。

- **Go**: `go build`相当のコンパイルチェックができないか検討する(ローカル/CI環境にGoツールチェインが必要になる可能性がある)
- **Java**: `javac`によるコンパイルチェック(サンドボックス内に`java`は存在することを確認済み、`javac`の有無も確認すること)
- **Swift / Kotlin / Rust / C# / Dart / PHP**: それぞれの言語のコンパイラ/インタプリタが実行環境にあるか確認し、なければCI(GitHub Actions)上でのセットアップを検討する。GitHub Actionsには各言語の公式setup action(`actions/setup-go`, `actions/setup-java`等)が存在するため、ローカルで全部揃える必要はなく、CIで担保する設計でもよい。**重要: ローカル開発環境(ぽぽのPC)に複数言語のコンパイラ/SDKを直接インストールすることは避けること。** Go, Java, Swift, Kotlin, Rust等のツールチェインは1つあたり数百MB〜1GB超になることがあり、ローカル環境を不必要に重くする。原則として、TypeScript/Python以外の言語の実処理系検証はGitHub Actions上でのみ実行し、ローカルの`npm install`や`package.json`には新たな重い依存を追加しない設計にすること。
- **GraphQL / Protobuf / JSON Schema**: 専用のスキーマバリデータ(`graphql-js`のパーサー、`protobufjs`、JSON Schemaバリデータ等)で構文・スキーマの妥当性を検証する。npm経由で導入できるものを優先する。
- **SQL/Prisma**: Prisma CLIのスキーマバリデーション(`prisma validate`相当)が使えるか検討する。

**この機能の検証における大原則**: 「出力に特定の文字列が含まれているか」のチェックだけで済ませず、可能な限りその言語の処理系に実際に解釈させて、エラーが出ないことを確認する設計にすること。処理系の導入が困難な言語がある場合は、その理由を明記し、代替の検証方法(構文木を構築できるパーサーライブラリの利用等)を検討する。

## 4. スコープの境界

**今回やること**
- Tier 1の全15ターゲットに対する、実処理系ベースの検証テストの追加・拡充
- 既存の`compile-check.test.ts`のテストケース(入力スキーマパターン)の拡充
- ローカル環境で処理系が用意できない言語については、GitHub Actions上でのCI実行に切り出す設計の検討

**今回やらないこと(明示的に対象外)**
- Tier 2(スキャフォールド/近似出力)ターゲットの品質検証は対象外。Tier 1を優先する。
- 新機能(影響範囲伝播・整合性チェッカー等)の実装は行わない。
- ジェネレーターのロジック自体の大規模リファクタリングは行わない。検証で見つかったバグの修正は対象とするが、設計変更は最小限にする。
- AI機能(Gemini連携)には触れない。本タスクの範囲外。

## 5. 受け入れ条件

- Tier 1の各ターゲットについて、「実処理系がエラーを出さずに通る」ことを検証するテストが最低1つ存在すること。
- 既存の140+テストが壊れないこと(`npx vitest run`)。
- 処理系をローカルで用意できなかった言語については、その理由と、CI側でどう担保するかの方針をコメントまたはドキュメントに残すこと。
- 検証の過程で実際のバグ(コンパイルエラー、型の誤り)が見つかった場合は、対象のジェネレーター(`src/lib/generators.ts`または`src/lib/generators-extended.ts`)を修正し、再現テストを残すこと。
- **テストを通すことを目的化して、出力の表現力を落とさないこと。** 例えば、union型・recursive型・ジェネリクスなど複雑な構造を生成するとコンパイラ検証で引っかかりやすいからといって、それらの構造自体を生成しないようにジェネレーターを単純化する、という対応は禁止する。検証で問題が見つかった場合は、まず「生成ロジックの誤り」と「検証基準が必要以上に厳しい」のどちらが原因かを判別し、後者であれば検証側(コンパイラオプション等)を調整すること。

## 6. 設計判断は実装者(Opus)に委ねる部分

- 各言語の処理系をどう実行環境に用意するか(ローカルのpackage.json devDependencies, Docker, CI上のみ等)
- テストの実行速度とCIへの影響をどう抑えるか(全テストを毎回フルセットで走らせるか、PRごとか等)
- 処理系の導入が現実的に困難な言語(例: 一部のニッチな言語)に対して、どこまで実処理系での検証を諦めて構文パーサーでの検証に留めるか

## 7. 参考: 優先順位の根拠

このタスクは新機能(`IMPACT_PROPAGATION_SPEC.md`)より先に着手すること。理由は、出力の正確性が保証されていない状態で新機能を追加しても、土台の信頼性が低いままでは製品全体の価値が積み上がらないため。

## 8. 実装後の確認ステップ(必須)

Claude Codeによる実装が完了したと報告された後、以下を必ず人間(ぽぽ)が確認すること。AIの「完了しました」という報告だけで次の作業に進まない。

- 実際に`npx vitest run`を自分の手元で実行し、全テストが通ることを目で見て確認する。
- 新規追加されたテストファイルの差分(git diff)を確認し、「本当に実処理系を呼んでいるか」「文字列マッチだけに後退していないか」を確認する。
- 修正されたジェネレーターについては、修正前後の出力を実際に1つ自分で見比べて、意図した変更だけが入っているか確認する。特に「複雑な構造(union型、recursive型等)に対応する出力が、検証を通すために簡略化・削除されていないか」を確認する。
- 「対象外」としたはずの範囲(Tier 2、新機能、AI機能)に変更が及んでいないか、変更されたファイルの一覧を確認する。
