# Feature Spec: Impact Propagation View

## 1. 背景・目的

TypeMorphは現在「Schema → AST → 160+言語への変換」を提供しているが、これは他のコンバーターツール(quicktype等)と同じ「一方通行変換」のカテゴリに属する。

この機能は、TypeMorphが持つ独自資産である **AST中間層** を活用し、「スキーマの1フィールドを変更したとき、それが他のどのクラス・どの出力言語に波及するか」を可視化する。これにより、TypeMorphを単なるコンバーターから「型安全性インフラ」のポジションに引き上げる、第一弾の機能と位置付けている。

**この機能だけでHacker News Show HNに出せる程度の、独立した価値を持つ機能にすること。**

### 競合状況(実装方針に影響するため共有)

調査の結果、「スキーマの破壊的変更検出」自体は既に複数のツールが手がけている。oasdiff(OpenAPI diff、300+検出ルール、1100+スター)、データベースCI/CDツール群(Liquibase等、SQLの影響分析・ドリフト検出)、APIShift(ライブAPIの変更を監視するSaaS)などが存在する。

ただし、これらは共通して**単一フォーマット内の前後比較**に限定されている(OpenAPIのみ、SQLのみ、REST APIのみ)。**「1つのスキーマ変更が、複数の異なる出力言語(TS/SQL/Zod/Go等)にどう横断的に波及するか」を1つのASTで見せるツールは確認できていない**。また競合は基本的にサーバー型/SaaS型であり、TypeMorphの「100%ブラウザローカル」という性質は競合に対する明確な差別化点になる。

実装にあたっては、この2点(言語横断・ローカル完結)を損なわない設計を優先すること。検出ルールの網羅性で競合(oasdiff等)に勝とうとする必要はない。

## 2. やりたいことの具体像

ユーザーが2つのスキーマ(変更前・変更後)を入力する、または既存スキーマの1フィールドを編集する。

その結果を以下の3つの状態に分類して提示する。

- **changed**: 直接変更されたフィールド/クラス
- **impacted**: 変更されたクラスを参照している(直接・間接含む)ため、影響を受けるクラス
- **safe**: 変更と無関係なクラス

提示する内容は2階層:

1. **クラス間の波及グラフ** — どのクラスがどのクラスに波及しているかを視覚的に表示
2. **出力言語ごとの影響** — 160+の生成対象言語のうち、どの言語の出力が実際に変わるか/再生成が必要かをリスト表示

ユーザーが「これは破壊的変更か」「どこを直せばいいか」を一目で理解できることがゴール。単なるdiff表示ではなく、**影響範囲がどこまで広がるかの全体像**を見せることに価値がある。

## 3. 再利用する既存資産(変更前提で読むこと)

実装の前に、最低限以下の既存ファイルを読んで、現在のロジックと設計意図を理解すること。

- `src/lib/diff.ts` — `compareSchemaTypes()` がフィールドレベルの破壊的変更を `SchemaDiff[]` として検出済み。severity分類(info/warning/error)あり。これを変更検出の入力として使う。
- `src/lib/graph.ts` — `extractTypeGraph()` が生成済みTSコードからクラス間の参照関係(`TypeNode`/`TypeEdge`)を抽出している。今は生成後のテキストを正規表現で読んでいるが、本機能ではAST(`src/lib/ast.ts`の`ASTClass[]`)から直接グラフを構築する方が望ましいかもしれない。どちらが適切かは設計判断に委ねる。
- `src/lib/ast.ts` — `schemaToAST()` がSchemaからASTClass配列を生成する。クラス名解決・継承・フラット化のロジックが既にあるので、これを壊さないこと。
- `src/components/TypeGraphPanel.tsx` — 既存のグラフ描画コンポーネント。レイヤードレイアウト(`layoutNodes`)とSVG描画を自前で実装している。**新しい描画ライブラリ(react-flow, d3等)は導入しない**。このコンポーネントのレイアウト/描画ロジックを拡張・再利用する方針とする。

## 4. スコープの境界

**今回やること**
- 1つのスキーマ変更が、AST上の他クラスにどう波及するかの検出ロジック
- 出力言語ごとに「影響を受けるか」を判定するロジック
- 上記をビジュアライズするUI(既存の`TypeGraphPanel`の延長)

**今回やらないこと(明示的に対象外)**
- 双方向同期(他フォーマットを編集してAST/他言語に逆伝播させる機能)は別フェーズ。今回は逆方向パーサーの新規実装はしない。
- マイグレーションSQL自動生成は別フェーズ。
- モノレポ全体のスキーマ整合性チェック(複数ファイルスキャン)は別フェーズ。
- 新規の外部グラフ描画ライブラリの導入はしない。

## 5. 受け入れ条件

- 既存のテスト(`npx vitest run`、140+件)が壊れないこと。
- `diff.ts`・`graph.ts`・`ast.ts`に変更を加える場合、対応する `*.test.ts` に新規ケースを追加すること。
- 新機能のコアロジック(変更検出→波及判定)に対するユニットテストを新規に追加すること。
- 既存の`TypeGraphPanel`のダークモード/ライトモード切り替え、パン・ズーム操作を引き継ぐこと。
- 100%ブラウザローカルで動作すること(サーバー処理・新規外部APIへの依存を増やさない)。

## 6. 設計判断は実装者(Opus)に委ねる部分

以下は意図的に決めていない。実装者が既存コードを読んだ上で最適な設計を判断すること。

- 波及判定をASTベースのグラフ探索にするか、既存の`extractTypeGraph`を拡張するか
- `SchemaDiff`のpath文字列と、ASTのクラス名/フィールド名をどうマッピングするか
- 出力言語ごとの影響判定をどの粒度で行うか(クラス単位か、フィールド単位か)
- UIコンポーネントを既存`TypeGraphPanel`に直接機能追加するか、新規コンポーネントとして切り出すか
- ハイライト状態(changed/impacted/safe)をpropsで渡す設計か、内部で計算する設計か

## 7. 参考: 視覚的方向性(イメージ共有用、デザインの最終決定権は実装者)

- 変更元のクラスは赤系、波及先はオレンジ系、無関係はグレーアウト、というグラデーションで「波及の強さ」を表現する
- グラフの下に、出力言語ごとの影響有無を並べたカードリストを置き、「結局どこを直せばいいか」が一目で分かるようにする
- 既存の`TypeGraphPanel`の slate ベースの配色・Linear的な落ち着いたスタイルを継承する

## 8. コピー・トーンの方針

製品全体として現在「Institutional-Grade」「Elite」「世界最高」のような誇張表現が使われているが、これは今回採用するポジショニング(下記)と矛盾するため、本機能のUI文言では避けること。

採用するポジショニング: **「サーバーに何も送らない、静かに信頼できるスキーマツール」**。機能の豊富さや派手さを訴える言葉より、「実際に何が起きるかを正確に、誇張なく説明する」文言を優先する。例: 「3 classes affected, 3 of 6 output languages need regeneration」のように、具体的な事実を淡々と示す表現が望ましい。「革命的」「業界最高」等の煽り文句はUI上では使わない。

## 9. 今後のロードマップ(参考情報、今回のスコープ外)

本機能は以下の順序で構想されている一連の機能群の最初の一歩。実装時にこの先を見据えた拡張性(特にAST周りの設計)を多少意識してもよいが、今回はあくまで1番のみを実装すること。

1. **(今回)Impact Propagation View** — 本スペック
2. **モノレポ整合性チェッカー** — リポジトリ内の複数スキーマ定義(SQL/OpenAPI/Zod/TS)間の不整合検出。既存パーサー群(`parseSQLToZod`, `parseTypeScriptToSchema`, `parseZodToSchema`, `parseOpenAPI`等)を横断的に走らせる想定。
3. **スキーマの考古学** — 2番の発展形。「どれが正しいか」を前提にせず、構造的に類似したスキーマ定義間の矛盾を検出・提示する。

双方向同期・マイグレーション自動生成・CI強制については、1番のリリース後の反応を見て採否を判断する段階のため、現時点では設計に含める必要はない。
