# TypeMorph Privacy Principles

このドキュメントは、TypeMorphに新機能を追加する際、「これはローカルで完結させるべきか、サーバーに送るべきか」を判断するための基準を定める。機能ごとの実装方法(具体的なAPI設計、認証フロー等)はここでは決めない。それは各機能のスペックを実装する際に、実装者(Opus)が判断する。

## 1. 大原則

**デフォルトはローカル完結。サーバーへのデータ送信は、ユーザーが明示的に選んだ場合のみ行う。**

「プライバシーを重視したい人」と「特に気にしない人」が、同じ製品の中で両方満足できることを目指す。プライバシー重視のユーザーには何も送信しない体験を、チーム機能等を必要とするユーザーには共有・同期の機能を、それぞれ提供する。どちらかに強制しない。

## 2. 判断フロー

新しい機能を作る際、以下の順に問うこと。

**Q1. この機能は、1人のユーザーのブラウザ内だけで完結できるか?**
→ Yes: ローカル実装する。サーバーとの通信は発生させない。これが可能な機能は常にこちらを優先する。
→ No(複数人のデータを横断する必要がある、リアルタイム共有が必要、等): Q2へ。

**Q2. サーバーに送る必要があるものは、「スキーマの内容そのもの」か、それとも「権限・認証情報」だけか?**
→ 権限・認証情報のみ(ログイン状態、ライセンスキー、サブスクリプション状態の確認等): 送信してよい。スキーマの内容は含めない。
→ スキーマの内容そのもの: Q3へ。

**Q3. その送信は、ユーザーが明示的に選択した結果か?**
→ Yes(例: 「チームと共有する」ボタンを押した、AI機能の利用に同意した): 送信してよい。ただし、何が送信されるかをユーザーに明示すること。
→ No(デフォルトの動作として自動的に送信される): 実装してはならない。設計を見直すこと。

## 3. 既存実装への当てはめ(参考)

今の実装は概ねこの原則に沿っている。新機能を作る際の比較対象として参考にすること。

- スキーマの推論・変換・diff検出・コード生成: すべてブラウザ内で実行。送信なし。原則に合致。
- Gumroadライセンス確認(`api.gumroad.com/v2/licenses/verify`): 権限情報のみ送信、スキーマ内容は含まない。原則に合致。
- Geminiプロキシ(`gemini-proxy`): ユーザーがAI機能の利用を選んだ場合のみ、その操作の対象データだけが送信される想定。原則に合致(実装時に「ユーザーの明示的な選択なしに自動送信されていないか」を都度確認すること)。

## 4. 今後機能を作る際の注意点(具体的設計はOpusに委ねる)

- 「チーム機能」=「全データをサーバーに送る」と短絡的に実装しない。ログイン・権限確認の部分と、データ共有の部分は分離して設計できないか、必ず検討する。
- モノレポ整合性チェッカーやスキーマの考古学のような、将来的に「複数人のリポジトリを横断する」可能性がある機能も、まずは「各メンバーのローカル環境、またはCI(GitHub Actions等)のランナー内で完結できないか」を先に検討する。TypeMorph社のサーバーを経由しない設計が可能であれば、それを優先する。
- どうしてもサーバーを介する必要がある機能を設計する場合は、何が・いつ・なぜ送信されるかをユーザーに明確に示すUI(送信前の確認、送信内容の表示等)を必ず含める。これも具体的なUIは実装者の判断に委ねるが、「ユーザーに見えない送信は作らない」という原則だけは固定する。

## 5. このドキュメントの位置づけ

各機能のスペック(例: `IMPACT_PROPAGATION_SPEC.md`)を実装する際、このドキュメントの原則と矛盾しないかを確認すること。矛盾する場合はこのドキュメントを優先し、機能スペック側の設計を見直す。
