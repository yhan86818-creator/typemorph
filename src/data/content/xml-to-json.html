XML to JSON: fast-xml-parser, Attribute Strategies, Namespace Handling, and SOAP Unwrapping

XML-to-JSON conversion has three hard problems that simple examples hide: attribute mapping (should id="42" become {"@id": "42"} or {"id": "42"}?), array detection (a single <role> child and three <role> children produce different shapes with naive parsers), and namespace handling (SOAP envelopes add soap:, ns0:, xsi: prefixes to every tag). This guide covers fast-xml-parser configuration for production use, the four attribute conventions (BadgerFish, GData, Parker, Rayfish), reliable always-array patterns, and a SOAP envelope unwrapper.

Live Example: fast-xml-parser Configuration

import { XMLParser } from 'fast-xml-parser';

// Input XML (user directory API response)
const xml = `
<UserResponse xmlns="http://api.example.com/v2" xmlns:meta="http://api.example.com/meta">
  <meta:timestamp>2024-03-15T10:30:00Z</meta:timestamp>
  <Users totalCount="3">
    <User id="101" active="true">
      <Name>Alice Chen</Name>
      <Role>Admin</Role>
    </User>
    <User id="102" active="false">
      <Name>Bob Kim</Name>
      <Role>Editor</Role>
    </User>
  </Users>
</UserResponse>`;

const parser = new XMLParser({
  // Attribute handling
  ignoreAttributes:        false,       // parse attributes (default: true = ignore)
  attributeNamePrefix:     '@_',        // prefix to distinguish attrs from elements
  attributeValueProcessor: (name, val) => {
    if (val === 'true') return true;    // coerce "true"/"false" to boolean
    if (val === 'false') return false;
    if (!isNaN(Number(val))) return Number(val);   // coerce numeric strings
    return val;
  },

  // Array handling — CRITICAL: ensures consistent shape regardless of child count
  isArray: (tagName) => ['User', 'Role', 'Permission', 'Item'].includes(tagName),

  // Namespace handling
  removeNSPrefix: true,     // strip "meta:", "soap:", "ns0:" prefixes from tag names

  // Text node handling
  textNodeName: '#text',    // element with both attributes and text content

  // Type coercion for element text
  parseTagValue: true,      // "42" → 42, "true" → true in element text

  // Trim whitespace from text nodes
  trimValues: true,
});

const result = parser.parse(xml);
console.log(JSON.stringify(result, null, 2));

// Output:
// {
//   "UserResponse": {
//     "timestamp": "2024-03-15T10:30:00Z",

//       "@_totalCount": 3,
//       "User": [           // always an array because of isArray config
//         { "@_id": 101, "@_active": true,  "Name": "Alice Chen", "Role": "Admin" },
//         { "@_id": 102, "@_active": false, "Name": "Bob Kim",    "Role": "Editor" }

The Four Attribute Conventions

// Input XML: <User id="42" status="active">Alice</User>

// 1. BadgerFish convention — most explicit, roundtrip-safe
// Attributes prefixed @, text node is $
{ "User": { "@id": "42", "@status": "active", "$": "Alice" } }

// 2. GData/Google convention — @-prefix but text in $t
{ "User": { "@id": "42", "@status": "active", "$t": "Alice" } }

// 3. Parker convention — flatten attrs, text as string (loses roundtrip)
// Only works when attrs and element names don't collide
{ "User": { "id": "42", "status": "active" } }  // "Alice" is lost unless text-only

// 4. Rayfish / fast-xml-parser default — customizable prefix
// fast-xml-parser with attributeNamePrefix: "@_"
{ "User": { "@_id": "42", "@_status": "active", "#text": "Alice" } }

// Choosing a convention:
// Roundtrip (JSON → XML → same JSON): use BadgerFish or GData
// One-way (XML → JSON for frontend): use Parker or Rayfish (cleaner output)
// SOAP/enterprise integration: use BadgerFish (tools like Mulesoft expect it)

The Array Detection Problem and Its Fix

// THE PROBLEM: different JSON shapes for same semantic data
// One child:   { "roles": { "role": "Admin" } }
// Two children:{ "roles": { "role": ["Admin", "Editor"] } }
// This breaks: response.roles.role.map(r => ...) — only works for the array case

// WRONG approach — handle it at runtime with type checks:
const roles = Array.isArray(data.roles.role) ? data.roles.role : [data.roles.role];

// RIGHT approach — force arrays in the parser configuration:
const parser = new XMLParser({
  isArray: (tagName, jPath, isLeaf, isAttribute) => {
    // By tag name (most common)
    const alwaysArray = ['role', 'permission', 'item', 'user', 'product'];
    if (alwaysArray.includes(tagName.toLowerCase())) return true;

    // By JSON path (more precise — avoids false positives)
    if (jPath === 'response.roles.role') return true;

    return false;
  },
});

// Now both cases produce the same shape:
// { "roles": { "role": ["Admin"] } }        // single child
// { "roles": { "role": ["Admin", "Editor"] } }  // multiple children

// TypeScript type: role is always string[]
interface Roles {
  role: string[];
}

SOAP Envelope Unwrapping

// SOAP responses have a mandatory envelope wrapper around the actual payload
// Input SOAP XML:
// <soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
//   <soap:Header>...</soap:Header>
//   <soap:Body>
//     <GetUserResponse>
//       <User id="42"><Name>Alice</Name></User>
//     </GetUserResponse>
//   </soap:Body>
// </soap:Envelope>

const soapParser = new XMLParser({
  ignoreAttributes: false,
  attributeNamePrefix: '@_',
  removeNSPrefix: true,   // strips soap: prefix — Envelope → Envelope
  isArray: (tag) => ['User', 'Order', 'Item'].includes(tag),
});

function unwrapSoap<T>(soapXml: string): T {
  const parsed = soapParser.parse(soapXml);
  const body   = parsed['Envelope']?.['Body'];
  if (!body) throw new Error('No SOAP Body in response');

  // Get the first child of Body (the actual response element)
  const responseKey = Object.keys(body)[0];
  return body[responseKey] as T;
}

interface GetUserResponse {
  User: Array<{ '@_id': number; Name: string }>;
}

const response = unwrapSoap<GetUserResponse>(soapXml);
// { User: [{ "@_id": 42, "Name": "Alice" }] }

// SOAP fault handling
function checkSoapFault(parsed: any): void {
  const fault = parsed?.Envelope?.Body?.Fault;
  if (fault) {
    throw new Error(`SOAP Fault: ${fault.faultcode} — ${fault.faultstring}`);
  }
}

Namespace Handling Strategies

// Option 1: removeNSPrefix: true (recommended for internal APIs)
// soap:Body → Body, ns0:User → User
// Loses namespace context — only safe if tag names are unique across namespaces

// Option 2: Keep namespace prefixes but normalize them
const parser = new XMLParser({
  removeNSPrefix: false,
  // Tags remain: "soap:Body", "ns0:User" — use bracket notation in JS
});

// Option 3: Namespace-aware parsing with xml2js
import xml2js from 'xml2js';

const result = await xml2js.parseStringPromise(xmlString, {
  explicitArray: false,      // single elements aren't wrapped in arrays
  tagNameProcessors: [xml2js.processors.stripPrefix],  // strip ns: prefixes
  attrNameProcessors: [xml2js.processors.stripPrefix],
  explicitCharkey: false,    // text content is a direct string, not { _: "..." }
});

// Option 4: Full namespace-aware parsing (for XSLT pipelines, cross-schema validation)
// Use saxes (SAX parser) or sax-js with namespace support
import { createParser } from 'saxes';

const parser2 = createParser({ xmlns: true });
parser2.on('opentag', node => {
  console.log(node.local);        // tag name without prefix
  console.log(node.uri);          // full namespace URI
  console.log(node.attributes);   // attribute map with namespace info
});

Best Practices for Production

  • Always configure isArray for repeating elements: Without it, a single-item list produces an object where a multi-item list produces an array. Your code must handle both shapes differently, which creates bugs. Whitelist every tag that logically represents a collection.
  • Use removeNSPrefix: true for one-way integrations: When your app only consumes XML (not produces it), stripping namespace prefixes simplifies access patterns. But document which namespaces were stripped so future maintainers understand why soap: tags aren't present.
  • Coerce attribute types explicitly: All XML attributes are strings. Numbers and booleans must be coerced manually using attributeValueProcessor in fast-xml-parser. An active="true" attribute without coercion becomes the string "true", which is truthy but fails === true checks.
  • Validate the parsed JSON with Zod before using it: XML services can change their schema, add new elements, or return error shapes without warning. A Zod schema at the parse boundary catches these issues at the point of ingestion, not buried in your business logic.

FAQ

Q: Which library should I use for XML parsing in Node.js in 2024+?
A: fast-xml-parser for most use cases — it's actively maintained, has zero dependencies, works in browsers and Node.js, and its configuration API handles the common cases cleanly. Use xml2js if you need the existing toolchain in a legacy project. Use saxes for large documents where SAX streaming is necessary, or for namespace-critical scenarios.

Q: How do I convert JSON back to XML (round-trip)?
A: fast-xml-parser includes an XMLBuilder class that produces XML from a JSON object. For lossless round-trips, use the BadgerFish convention (attributes as @*, text as $) which preserves the distinction between attributes, text nodes, and element children. Conventions that flatten attributes (Parker) lose information and can't reconstruct the original XML.

Q: How do I handle mixed content (text and elements interleaved)?
A: Mixed content (like <p>Hello <b>world</b>!</p>) is the hardest case in XML-to-JSON. fast-xml-parser can capture text nodes with the textNodeName option, but the interleaved ordering is lost. For HTML-like mixed content, use an HTML parser (parse5, htmlparser2) instead of an XML parser, then convert the resulting AST to JSON.
