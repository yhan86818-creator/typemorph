JSON to Playwright Test: API Testing, HAR Replay, and Full-Platform E2E Automation

Playwright is not just a browser automation library — it is a full test platform. Beyond click-and-assert UI tests, Playwright can test your REST APIs directly without opening a browser, record all network traffic as a HAR file and replay it deterministically in CI, run tests in parallel across Chromium, Firefox, and WebKit from a single config, and generate full execution traces that let you debug production failures minutes after they happen. Converting your JSON data into Playwright tests unlocks all of these capabilities.

Live Example: Data-Driven Tests with Type-Safe JSON Fixtures

// fixtures/users.json
[
  { "username": "admin",  "role": "administrator", "canDelete": true  },
  { "username": "editor", "role": "editor",        "canDelete": false },
  { "username": "viewer", "role": "viewer",        "canDelete": false }
]

// tests/role-permissions.spec.ts
import { test, expect } from '@playwright/test';
import users from '../fixtures/users.json';

for (const user of users) {
  test(`${user.role} sees correct permissions`, async ({ page }) => {
    await page.goto('/login');
    await page.fill('[data-testid="username"]', user.username);
    await page.fill('[data-testid="password"]', 'test-password');
    await page.click('[data-testid="submit"]');

    await expect(page).toHaveURL('/dashboard');

    const deleteButton = page.locator('[data-testid="delete-btn"]');
    if (user.canDelete) {
      await expect(deleteButton).toBeVisible();
    } else {
      await expect(deleteButton).not.toBeVisible();
    }
  });
}

Playwright generates a named test for each JSON entry, so the test report shows administrator sees correct permissions rather than an anonymous parameterized index. When one scenario fails, the trace pinpoints exactly which user role broke.

API Testing with the request Fixture

Playwright's request fixture lets you test JSON API endpoints without a browser — full HTTP client, cookie handling, and response assertions, all in the same test runner:

import { test, expect } from '@playwright/test';

const newUser = {
  name: "Alice Smith",
  email: "alice@example.com",
  role: "editor"
};

test('POST /api/users creates a user', async ({ request }) => {
  const response = await request.post('/api/users', {
    data: newUser,
    headers: { 'Content-Type': 'application/json' }
  });

  expect(response.status()).toBe(201);
  const body = await response.json();
  expect(body.id).toMatch(/^usr_/);
  expect(body.email).toBe(newUser.email);
  expect(body.role).toBe(newUser.role);
});

test('GET /api/users/:id returns the created user', async ({ request }) => {
  const create = await request.post('/api/users', { data: newUser });
  const { id } = await create.json();

  const get = await request.get(`/api/users/${id}`);
  expect(get.status()).toBe(200);
  const user = await get.json();
  expect(user.name).toBe(newUser.name);
});

API tests run without a browser context — 10-20× faster than UI tests. Use them for your critical JSON API contracts; they catch breaking changes before the UI test suite even starts.

Network Mocking with page.route()

Mock any network request with a JSON response to isolate the UI from a flaky or unavailable backend:

// api-responses/products.json
{
  "items": [
    { "id": "p1", "name": "Widget Pro",  "price": 49.99, "inStock": true  },
    { "id": "p2", "name": "Widget Lite", "price": 19.99, "inStock": false }
  ],
  "total": 2
}

test('product list renders from mocked API', async ({ page }) => {
  await page.route('**/api/products**', route =>
    route.fulfill({
      status: 200,
      contentType: 'application/json',
      path: './api-responses/products.json',
    })
  );

  await page.goto('/products');
  await expect(page.locator('[data-testid="product-card"]')).toHaveCount(2);
  await expect(page.locator('text=Widget Pro')).toBeVisible();
  await expect(
    page.locator('[data-testid="p2"] [data-testid="out-of-stock"]')
  ).toBeVisible();
});

// Simulate API errors
test('shows error state on 500', async ({ page }) => {
  await page.route('**/api/products**', route =>
    route.fulfill({ status: 500, body: '{"error":"Internal Server Error"}' })
  );

  await page.goto('/products');
  await expect(page.locator('[data-testid="error-message"]')).toBeVisible();
});

HAR Recording and Replay for Network-Isolated CI

HAR (HTTP Archive) files are JSON — every request and response captured in a standard format. Playwright can record HAR once and replay it in CI with no external dependencies:

// Record HAR during development (run once)
test('record product page traffic', async ({ page }) => {
  await page.routeFromHAR('./hars/product-page.har', { update: true });
  await page.goto('/products/p1');
  // All network calls are captured to product-page.har
});

// Replay HAR in CI — completely network-isolated
test('product page renders from HAR', async ({ page }) => {
  await page.routeFromHAR('./hars/product-page.har', {
    url: '**/api/**',
    notFound: 'abort',   // fail if a request is not in the HAR
  });

  await page.goto('/products/p1');
  await expect(page.locator('h1')).toContainText('Widget Pro');
  await expect(page.locator('[data-testid="price"]')).toContainText('$49.99');
});

HAR replay makes tests hermetic — identical JSON responses on every run, no flaky external API calls, no test data cleanup between runs. Teams check HAR files into the repo alongside their spec files and regenerate them when the API contract changes.

Fixture-Based Dependency Injection with test.extend()

Playwright fixtures let you inject authenticated state and shared test data using test.extend():

// test-fixtures.ts
import { test as base } from '@playwright/test';
import type { Page } from '@playwright/test';
import adminCredentials from './data/admin.json';

type TestFixtures = {
  authenticatedPage: Page;
  apiToken: string;
};

export const test = base.extend<TestFixtures>({
  apiToken: async ({ request }, use) => {
    const resp = await request.post('/api/auth/token', {
      data: adminCredentials,
    });
    const { token } = await resp.json();
    await use(token);
    // teardown: nothing to do — token expires
  },

  authenticatedPage: async ({ page, apiToken }, use) => {
    await page.addInitScript(token => {
      window.localStorage.setItem('auth_token', token);
    }, apiToken);
    await use(page);
  },
});

// tests/dashboard.spec.ts
import { test } from '../test-fixtures';
import { expect } from '@playwright/test';

test('admin can access user management', async ({ authenticatedPage }) => {
  await authenticatedPage.goto('/dashboard');
  await expect(authenticatedPage.locator('[data-testid="user-table"]')).toBeVisible();
});

Fixtures compose — authenticatedPage depends on apiToken, which depends on request. Playwright resolves the dependency graph automatically and tears down in reverse order after each test.

Trace Viewer for CI Debugging

Configure traces to capture on first retry, then open the interactive viewer to replay every action with full DOM snapshots and network details:

// playwright.config.ts
export default defineConfig({
  use: {
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit',   use: { ...devices['Desktop Safari'] } },
  ],
  workers: process.env.CI ? 4 : undefined,
});

# Download trace.zip from CI artifact and open locally
npx playwright show-trace trace.zip

The trace viewer shows a step-by-step timeline with before/after DOM snapshots, all network requests with JSON bodies and response payloads, console logs, and screenshots. You can debug a CI failure that happened on WebKit without a Mac.

Best Practices for Production

  • Use data-testid attributes: Don't select by CSS class or text content — both change with design updates. Treat data-testid as part of the public API contract between UI and tests.
  • Keep JSON fixtures minimal: Include only the fields your test actually exercises. A fixture with all 40 user fields obscures which 3 actually matter for the scenario being tested.
  • Separate API tests from UI tests: Fast API tests (no browser, ~50ms each) should run first and gate the UI test suite. If the API is broken, there is no value in loading a browser.
  • Use expect.soft() for multi-field JSON assertions: expect.soft() records a failure but continues the test — useful for checking a dozen fields in a response body without stopping at the first mismatch.
  • Use storageState for auth: Log in once in globalSetup, save browser storage state to auth.json, and load it in tests that need authentication. This eliminates redundant login sequences across your test suite.

FAQ

Q: Playwright or Cypress — which should I choose?
A: Playwright is better for multi-browser coverage (especially Safari/WebKit), API testing without a browser, parallel execution across machines, and teams running in CI-first workflows. Cypress is better for teams that value interactive debugging during development — its real-time test runner and time-travel snapshots reduce the feedback loop when writing new tests locally.

Q: Can Playwright test mobile apps?
A: Playwright emulates mobile browsers via the devices dictionary (iPhone 15, Pixel 7, etc.), setting viewport, User-Agent, and touch events. It does not test native iOS/Android apps — use Appium or Detox for native mobile.

Q: How do I handle authentication in every test?
A: Use storageState — log in once in globalSetup, save the browser's storage state to a JSON file (auth.json), and reference it in playwright.config.ts. All tests load that state and start already authenticated.

Q: How do I run Playwright in GitHub Actions?
A: Use npx playwright install --with-deps in your workflow to install browsers. Set workers: 4 in config to parallelize. Upload playwright-report/ as an artifact to access HTML reports and trace files after a CI failure.

Q: What is the difference between page.route() and HAR replay?
A: page.route() lets you intercept specific URLs and respond inline — flexible for mocking one or two endpoints in a test. HAR replay captures and replays all network traffic holistically — better for isolating a full page or flow from any external dependency. Use route() for targeted mocking, HAR for full network isolation.
