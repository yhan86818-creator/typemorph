JSON to NestJS DTO: class-validator デコレーターを一瞬で生成

NestJS では class-validator と class-transformer でデコレーションされた DTO クラスを使ってリクエストを検証します。エンドポイントごとに手書きするのは時間がかかり、デコレーターのミスが原因で不正なデータがサービス層に到達するリスクもあります。TypeMorph は実際の JSON サンプルから形状を推論し、デコレーター付きの完全な DTO を即座に生成します。

実例: API ペイロードから検証済み DTO へ

// 入力 JSON（POST /orders ボディ）
{
  "order_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "customer_email": "buyer@example.com",
  "total_amount": 12800.50,
  "item_count": 3,
  "is_gift": false,
  "note": null,
  "items": [
    { "product_id": "p001", "name": "Widget", "quantity": 2 }
  ]
}

// 生成された NestJS DTO
import { IsUUID, IsEmail, IsNumber, IsInt, IsBoolean, IsOptional,
         IsNotEmpty, IsArray, ValidateNested } from 'class-validator';
import { Type } from 'class-transformer';

export class OrderItemDto {
  @IsNotEmpty()
  product_id!: string;

  @IsNotEmpty()
  name!: string;

  @IsInt()
  quantity!: number;
}

export class OrderDto {
  @IsUUID()
  order_id!: string;

  @IsEmail()
  customer_email!: string;

  @IsNumber()
  total_amount!: number;

  @IsInt()
  item_count!: number;

  @IsBoolean()
  is_gift!: boolean;

  @IsOptional()
  note?: string | null;

  @IsArray()
  @ValidateNested({ each: true })
  @Type(() => OrderItemDto)
  items!: OrderItemDto[];
}

セットアップ手順

1. 依存関係をインストール： npm install class-validator class-transformer
2. tsconfig.json でデコレーターを有効化： "experimentalDecorators": true と "emitDecoratorMetadata": true を設定します。
3. ValidationPipe をグローバルに適用： main.ts に app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true })) を追加します。
4. JSON を貼り付け TypeMorph に JSON サンプルを入力し、NestJS DTO を選択して出力をコピーします。
5. レビューと調整： 数値には @Min()/@Max()、文字列には @Length()、既知のリテラル値には @IsEnum() を追加しましょう。

技術解説: デコレーターの推論ロジック

TypeMorph はフィールド名だけでなく、JSON の実際の値を分析して適切なデコレーターを選択します。UUID v4 パターンに一致する文字列は @IsUUID()、RFC-5322 形式のメールアドレスは @IsEmail()、ISO 8601 タイムスタンプは @IsISO8601() になります。整数値は @IsInt()、小数を含む数値は @IsNumber() です。ネストされたオブジェクトは別の DTO クラスとして生成され、@ValidateNested({ each: true }) と @Type() で接続されます—これは class-transformer が再帰的にインスタンス化・検証するために必要な組み合わせです。

比較: class-validator vs Zod vs tRPC

class-validator は、@nestjs/swagger を使った OpenAPI ドキュメント自動生成を活用するデコレーター中心の NestJS プロジェクトに最適です。Zod は tsconfig のフラグ不要でポータブルなため、フロントエンドとバックエンドで共有しやすい選択肢です。tRPC は API の両端を自分でコントロールできる場合に DTO 層自体を不要にします。

本番環境でのベストプラクティス

  • whitelist: true を使う： ValidationPipe が未知のプロパティを自動で除去し、マスアサインメント脆弱性を防ぎます。
  • リクエスト DTO とレスポンス DTO を分ける： CreateOrderDto（入力用）と OrderResponseDto（出力用）を分けることで、API の境界を明確に保ちます。
  • @Transform() で型変換： クエリパラメーターは文字列で届くため、@Transform(({ value }) => Number(value)) でバリデーション前に変換します。
  • @ApiProperty() と組み合わせる： @nestjs/swagger はデコレーターのメタデータを読み取って OpenAPI ドキュメントを自動生成します。

よくある質問

Q: 生成された DTO が !: string（確定的代入アサーション）を使っているのはなぜ？
A: NestJS DTO は class-transformer によってインスタンス化され、TypeScript のコンストラクターをバイパスします。! はコンパイラーに「ランタイムで必ず代入される」と伝えるためです。

Q: @nestjs/swagger と組み合わせられますか？
A: はい。各プロパティの上に @ApiProperty() を追加するだけで、バリデーションデコレーターと Swagger デコレーターは干渉しません。

Q: nullable フィールドはどう扱われますか？
A: JSON サンプルで null だったフィールドは @IsOptional() と string | null 型になります。
