JSON to Zod: TypeScript の型と一致するランタイムバリデーション

TypeScript の型はコンパイル後に消えてしまうため、不正な API レスポンス、想定外の形のフォーム送信、フィールドが欠けたデータベースレコードからあなたを守ってはくれません。Zod はそのギャップを埋めます。JSON から Zod スキーマを生成すれば、TypeScript の型とランタイムのバリデータを「単一の真実の源」から同時に得られるため、両者が食い違うことがありません。

実例: API レスポンスの検証

// API から受け取った JSON
{
  "api_version": "v2",
  "status": "success",
  "data": {
    "count": 42,
    "items": [
      { "id": "p_001", "name": "Widget", "price": 19.99, "in_stock": true }
    ]
  }
}

// 生成された Zod スキーマ
import { z } from 'zod';

const ItemSchema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1),
  price: z.number().positive(),
  in_stock: z.boolean(),
});

const ApiResponseSchema = z.object({
  api_version: z.string(),
  status: z.enum(['success', 'error']),
  data: z.object({
    count: z.number().int().nonnegative(),
    items: z.array(ItemSchema),
  }),
});

export type ApiResponse = z.infer<typeof ApiResponseSchema>;
export type Item = z.infer<typeof ItemSchema>;

parse() と safeParse() ― 正しい入口を選ぶ

Zod には2つのパースモードがあり、間違った方を選ぶのはよくあるミスです。

// parse() ― 失敗すると ZodError を投げる
// 用途: サーバー起動時の検証、テスト、CI チェック
const config = ConfigSchema.parse(process.env);

// safeParse() ― { success, data } または { success, error } を返す
// 用途: ユーザー入力、API レスポンスなどエラーを丁寧に扱いたい場面
const result = UserSchema.safeParse(req.body);
if (!result.success) {
  const errors = result.error.flatten().fieldErrors;
  return res.status(400).json({ errors });
}
const user = result.data; // 完全に型付けされた User

目安: 絶対に間違ってはいけないもの（起動時のアプリ設定）には parse()、失敗が想定され回復可能な外部データには safeParse() を使います。

判別可能なユニオン（discriminatedUnion）

API が type フィールドによって構造の変わるオブジェクトを返す場合、Zod の discriminatedUnion が正確な検証と網羅的な型チェックを提供します。

const ClickEventSchema = z.object({
  type: z.literal('click'),
  x: z.number(),
  y: z.number(),
});

const KeypressEventSchema = z.object({
  type: z.literal('keypress'),
  key: z.string(),
  ctrlKey: z.boolean(),
});

const DomEventSchema = z.discriminatedUnion('type', [
  ClickEventSchema,
  KeypressEventSchema,
]);

type DomEvent = z.infer<typeof DomEventSchema>;

可能なときは union より discriminatedUnion を使いましょう。判別子を最初にチェックするため高速で、エラーメッセージも分かりやすくなります。

省略可能（optional）と null 許容（nullable）の扱い

const UserSchema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1),
  email: z.string().email(),
  bio: z.string().optional(),          // キー自体が存在しないかもしれない
  deletedAt: z.string().nullable(),    // キーは存在するが null かもしれない
  nickname: z.string().nullish(),      // 存在しない、または null
});

// PATCH エンドポイント向け ― 全フィールドを optional に
const UpdateUserSchema = UserSchema.partial();

よくある落とし穴

  • z.infer を使わない: Zod スキーマと TypeScript の型を別々に手書きすると食い違います。必ず type User = z.infer<typeof UserSchema> のように型を導出しましょう。
  • クエリパラメータに z.coerce を忘れる: URL のクエリは常に文字列です。z.number() は "42" で失敗するため z.coerce.number() を使います。
  • 1つのスキーマに深くネストしすぎる: 5階層のネストは読みにくくテストも困難です。AddressSchema などの名前付きサブスキーマに分割して組み合わせましょう。

よくある質問

Q: optional と nullable の違いは?
A: .optional() はキーが存在しないことを許します（T | undefined）。.nullable() は値が null になりうることを表します（T | null）。.nullish() はその両方（T | null | undefined）です。

Q: z.union と z.discriminatedUnion の違いは?
A: z.union は各スキーマを順に試すため最悪 O(n) です。z.discriminatedUnion は判別子フィールドで一致するスキーマへ直接ジャンプするため O(1) です。共通の type や kind を持つなら常に後者を選びましょう。

Q: トップレベルが配列の JSON も検証できる?
A: できます。const TagsSchema = z.array(z.string().min(1)).min(1).max(20) のように、オブジェクトに包まず配列を直接検証できます。
