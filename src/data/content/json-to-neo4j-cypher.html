JSON to Neo4j Cypher: MERGE, UNWIND, and Graph Data Model Design

Neo4j stores data as a property graph: nodes (entities) connected by typed, directed relationships. Converting JSON to Cypher requires two distinct decisions: the data model decision (which JSON fields become node labels, which become relationship types, and which JSON keys become separate nodes vs. inline properties) and the ingestion strategy (individual MERGE vs. UNWIND bulk loading vs. APOC JSON import). Getting the graph model right upfront matters because refactoring a graph schema is harder than in relational databases — traversal queries depend on relationship types that can't be easily renamed in bulk.

Live Example: Social Network Data

// Input JSON (user with follows and interests)
{
  "user": {
    "id":       "usr_001",
    "name":     "Alice Chen",
    "email":    "alice@example.com",
    "joined":   "2023-06-15",
    "location": "San Francisco, CA",
    "country":  "US"
  },
  "follows": ["usr_002", "usr_003", "usr_007"],
  "interests": ["TypeScript", "Rust", "GraphQL"],
  "recent_activity": [
    { "type": "post",     "target_id": "post_100", "at": "2024-01-15T10:30:00Z" },
    { "type": "liked",    "target_id": "post_101", "at": "2024-01-15T11:00:00Z" },
    { "type": "commented","target_id": "post_102", "at": "2024-01-15T11:30:00Z" }
  ]
}

// Generated Cypher — idempotent with MERGE
// Step 1: Create user node (MERGE = create if not exists, match if exists)
MERGE (u:User {id: 'usr_001'})
SET   u.name     = 'Alice Chen',
      u.email    = 'alice@example.com',
      u.joined   = date('2023-06-15'),
      u.country  = 'US';

// Step 2: Create interest nodes and relationships
MERGE (i:Interest {name: 'TypeScript'})
MERGE (u:User {id: 'usr_001'})
MERGE (u)-[:INTERESTED_IN]->(i);

// Step 3: Create follow relationships
MERGE (u1:User {id: 'usr_001'})
MERGE (u2:User {id: 'usr_002'})
MERGE (u1)-[f:FOLLOWS]->(u2)
SET   f.since = date('2024-01-10');

UNWIND: Bulk Ingestion from JSON Arrays

Single MERGE statements are slow for large datasets. UNWIND processes an entire JSON array in one Cypher statement — much faster and maintains transactional consistency:

// Bulk-create users from a JSON array (via driver parameter)
// Node.js with neo4j-driver:

const session = driver.session();
const users = [
  { id: 'usr_001', name: 'Alice Chen', email: 'alice@example.com', country: 'US' },
  { id: 'usr_002', name: 'Bob Smith',  email: 'bob@example.com',   country: 'CA' },
  // ... thousands more
];

await session.run(
  `UNWIND $users AS u
   MERGE (n:User {id: u.id})
   SET   n.name    = u.name,
         n.email   = u.email,
         n.country = u.country`,
  { users }
);

// Bulk-create follow relationships
const follows = [
  { fromId: 'usr_001', toId: 'usr_002', since: '2024-01-10' },
  { fromId: 'usr_001', toId: 'usr_003', since: '2024-01-11' },
];

await session.run(
  `UNWIND $follows AS f
   MATCH  (a:User {id: f.fromId})
   MATCH  (b:User {id: f.toId})
   MERGE  (a)-[r:FOLLOWS]->(b)
   SET    r.since = date(f.since)`,
  { follows }
);

Constraints and Indexes (Required Before Bulk Import)

// ALWAYS create constraints before loading data
// Constraints create implicit indexes — MERGE on a constrained property uses the index
// Without constraints, MERGE on id does a full node scan (O(n) per MERGE call)

// Uniqueness constraint + index (one command in Neo4j 5.x)
CREATE CONSTRAINT user_id_unique
FOR (u:User)
REQUIRE u.id IS UNIQUE;

CREATE CONSTRAINT interest_name_unique
FOR (i:Interest)
REQUIRE i.name IS UNIQUE;

CREATE CONSTRAINT post_id_unique
FOR (p:Post)
REQUIRE p.id IS UNIQUE;

// Regular index for lookup-only (no uniqueness)
CREATE INDEX user_country FOR (u:User) ON (u.country);
CREATE INDEX user_joined  FOR (u:User) ON (u.joined);

// Check existing constraints
SHOW CONSTRAINTS;
SHOW INDEXES;

Graph Data Model Decisions

// KEY DESIGN QUESTION: When does a JSON value become its own node
// vs. an inline property on an existing node?

// RULE: Separate node when:
// 1. It has its own properties (a city has population, timezone)
// 2. Multiple entities reference it (many users share a city)
// 3. You traverse TO it (find all users in a city)

// INLINE PROPERTY when:
// 1. It's a simple scalar descriptor (user.country = 'US')
// 2. You rarely query on it independently
// 3. It's unique per entity

// EXAMPLE: Location as inline property vs. node

// Pattern A: inline property (simpler, fewer nodes)
MERGE (u:User {id: 'usr_001'})
SET u.city = 'San Francisco', u.country = 'US'

// QUERY: Find all users in San Francisco
MATCH (u:User {city: 'San Francisco'}) RETURN u  // full scan if no index

// Pattern B: separate City node (better for traversal)
MERGE (u:User {id: 'usr_001'})
MERGE (c:City {name: 'San Francisco', country: 'US'})
MERGE (u)-[:LIVES_IN]->(c)

// QUERY: Find all users in San Francisco — traversal, uses relationship index
MATCH (c:City {name: 'San Francisco'})-[:LIVES_IN]-(u:User) RETURN u

// QUERY: Find cities with the most users
MATCH (c:City)<-[:LIVES_IN]-(u:User)
RETURN c.name, COUNT(u) AS residents
ORDER BY residents DESC

APOC: Loading JSON from Files and URLs

// APOC (Awesome Procedures on Cypher) provides JSON loading utilities
// Install: neo4j-admin install-plugin apoc (or from Neo4j Desktop)

// Load from a local JSON file (must be in neo4j import directory)
CALL apoc.load.json('file:///users.json') YIELD value
WITH value AS data
UNWIND data.users AS u
MERGE (n:User {id: u.id})
SET   n.name  = u.name,
      n.email = u.email;

// Load from an HTTP URL (requires apoc.import.file.use_neo4j_config=false)
CALL apoc.load.json('https://api.example.com/users') YIELD value
WITH value.data AS users
UNWIND users AS u
MERGE (n:User {id: u.id})
SET n += u;  // SET n += map: updates all properties from the map

// APOC periodic commit for large files (avoids OutOfMemory)
CALL apoc.periodic.iterate(
  "CALL apoc.load.json('file:///large_events.json') YIELD value",
  "MERGE (e:Event {id: value.id}) SET e += value",
  {batchSize: 10000, iterateList: false, parallel: false}
)
YIELD batches, total, errors
RETURN batches, total, errors;

Traversal Queries on Loaded Data

// After loading, the graph enables traversal queries impossible in SQL

// Find users with mutual follows (friends of friends)
MATCH (alice:User {id: 'usr_001'})-[:FOLLOWS]->(mutual)<-[:FOLLOWS]-(other)
WHERE NOT (alice)-[:FOLLOWS]->(other) AND alice <> other
RETURN other.name, COUNT(mutual) AS common_follows
ORDER BY common_follows DESC
LIMIT 10;

// Shortest path between two users
MATCH path = shortestPath(
  (a:User {id: 'usr_001'})-[:FOLLOWS*..6]->(b:User {id: 'usr_099'})
)
RETURN [n IN nodes(path) | n.name] AS connection_path,
       length(path) AS degrees;

// Interest-based recommendations
MATCH (alice:User {id: 'usr_001'})-[:INTERESTED_IN]->(topic)
      <-[:INTERESTED_IN]-(other:User)
WHERE NOT (alice)-[:FOLLOWS]->(other) AND alice <> other
WITH other, COUNT(DISTINCT topic) AS shared_interests
ORDER BY shared_interests DESC
LIMIT 5
RETURN other.name, shared_interests;

Best Practices for Production

  • Create constraints before loading data, not after: Every MERGE (u:User {id: value}) without a uniqueness constraint on User.id performs a full label scan to check for duplicates — O(n) per row. A uniqueness constraint adds an index, making MERGE O(log n). For a million-row import, this is the difference between minutes and hours.
  • Use MERGE, not CREATE, for nodes referenced by multiple records: If multiple events reference the same user, CREATE creates duplicate user nodes. MERGE (u:User {id: 'usr_001'})` ensures exactly one node regardless of how many times it appears in your input data.
  • Separate node creation from relationship creation: MERGE node first, MERGE relationship second. Don't try to create both in one complex MERGE pattern — it's harder to debug and can create unexpected nodes when properties don't match.
  • Use relationship properties for time-based data: Store the timestamp, weight, or context on the relationship, not on either node. A FOLLOWS relationship's since property is the right place for when the follow happened — not on the User node where it would conflict with multiple relationships.

FAQ

Q: When should I use Neo4j vs. a relational database for JSON data?
A: Neo4j excels when relationships between entities are the primary query concern — social graphs, recommendation engines, fraud detection (who is connected to whom), knowledge graphs, and access control hierarchies. For simple CRUD with occasional joins, PostgreSQL is faster and simpler. The rule of thumb: if your queries have more than 2-3 JOIN hops in SQL, graph traversal is likely faster and simpler.

Q: How do I handle JSON arrays — as node properties or as separate nodes?
A: Store as property (String array) when elements are simple scalars you display but don't traverse to. Create separate nodes when elements are entities you join/traverse through — e.g., interests/tags as nodes enables MATCH (u)-[:INTERESTED_IN]->(t:Topic)<-[:INTERESTED_IN]-(other) which is impossible with a string array property.

Q: What's the best way to handle updates to existing nodes?
A: MERGE (n:User {id: u.id}) SET n += u where += merges properties from the map onto the node, updating existing keys and adding new ones without removing unlisted keys. Use SET n = u to replace all properties (removes keys not in the map). Use ON CREATE SET n.created = timestamp() and ON MATCH SET n.updated = timestamp() for audit timestamps.
