The SWIFT MT103 message is the global standard for single customer credit transfers — essentially, the financial industry's equivalent of a wire transfer instruction. Alongside MT202 (interbank transfers), MT103 is one of the two most critical message types in the cross-border payments ecosystem, processing trillions of dollars in transactions daily across the SWIFT network.

For payments engineers, integration architects, and fintech developers, the ability to parse MT103 messages and convert them to structured JSON is foundational to building modern payment rails, compliance systems, and reconciliation pipelines.

Anatomy of a SWIFT MT103 Message

An MT103 message is divided into four blocks, each enclosed in curly braces:

  • Block 1 (Basic Header): Contains the application identifier, session, and sequence number
  • Block 2 (Application Header): Input/Output indicator, message type (103), and destination BIC
  • Block 3 (User Header): Optional fields including banking priority, unique message ID
  • Block 4 (Text Block): The actual payment instruction data — the core of the message

Critical MT103 Field Tags and Their JSON Mappings

The text block (Block 4) of an MT103 contains the following mandatory and optional fields:

  • :20: (Transaction Reference Number) — Maps to transactionReference in JSON. A unique identifier assigned by the sender. Maximum 16 characters, alphanumeric.
  • :23B: (Bank Operation Code) — Maps to bankOperationCode. Always "CRED" for standard credit transfers. Other values: SPAY, SSTD, SPRI.
  • :32A: (Value Date, Currency, Amount) — Maps to a structured JSON object: { "valueDate": "YYYYMMDD", "currency": "USD", "amount": "10000.00" }. Critical: MT103 uses comma as decimal separator; JSON conversion must normalize to period.
  • :50K: or :50A: (Ordering Customer) — Maps to orderingCustomer with sub-fields for account, name, and address. 50K is the most common variant, containing unstructured free-text name/address lines.
  • :56A: or :56C: (Intermediary Institution) — Optional. Maps to intermediaryInstitution with BIC or clearing code.
  • :57A: or :57C: (Account With Institution) — The beneficiary's bank. Maps to accountWithInstitution with BIC and account details.
  • :59: or :59A: (Beneficiary Customer) — The ultimate recipient. Maps to beneficiaryCustomer with IBAN or account number, name, and address.
  • :70: (Remittance Information) — Free-text payment reference, up to 4 lines of 35 characters. Maps to remittanceInformation array in JSON.
  • :71A: (Details of Charges) — Charge allocation: SHA (shared), OUR (sender pays all), BEN (beneficiary pays all). Maps to chargesBearer enum.

Compliance and Security Considerations

MT103 messages contain a combination of PII (personal names, addresses), financial data (account numbers, IBANs, transaction amounts), and proprietary business information (payment references, invoice numbers). Under GDPR Article 25 (Data Protection by Design), processing this data should occur in the most privacy-preserving manner possible.

TypeFlow's MT103-to-JSON parser runs entirely in your browser's Web Worker thread. The message is parsed using a local JavaScript engine with zero network I/O during processing. This makes TypeFlow the only appropriate tool for handling production SWIFT data in a development or testing context — particularly for teams operating under SOC2 Type II, PCI-DSS, or DORA compliance frameworks.

Use Cases for MT103 JSON Conversion

  • ISO 20022 Migration: As a stepping stone before full MX adoption, converting MT103 to JSON allows intermediary processing and validation before generating pacs.008 XML.
  • Sanctions Screening Integration: Structured JSON can be directly fed into OFAC/EU sanctions screening APIs (e.g., Refinitiv World-Check) for automated compliance checks.
  • Reconciliation Systems: JSON-format MT103 data integrates cleanly with accounting systems and ERP platforms for automated payment reconciliation.
  • Audit Trail Generation: Storing MT103 payments as structured JSON in document databases (MongoDB, Firestore) enables powerful querying and reporting for regulatory audits.
