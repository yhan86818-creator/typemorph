JSON to Terraform: .tf.json Files, for_each Dynamic Resources, and Remote State

Terraform natively supports JSON as an alternative to HCL — files ending in .tf.json are parsed exactly like .tf files. This makes JSON-to-Terraform conversion practical for infrastructure automation: you can generate .tf.json files from API responses, config management databases, or CI/CD pipelines without a templating engine. Beyond static conversion, the most powerful pattern is using for_each with a JSON-derived map to provision many resources from a single resource block — a pattern used to manage dozens of S3 buckets, IAM policies, or Cloud Functions from one configuration file.

Live Example: .tf.json vs HCL

// Input JSON: cloud infrastructure spec
{
  "project": "myapp-prod",
  "region": "us-east-1",
  "s3_buckets": [
    { "name": "myapp-assets", "versioning": true,  "public": false },
    { "name": "myapp-logs",   "versioning": false, "public": false },
    { "name": "myapp-backups","versioning": true,  "public": false }
  ],
  "tags": { "Environment": "prod", "Team": "platform" }
}

// Generated .tf.json (main.tf.json) — Terraform reads this natively
{
  "terraform": {
    "required_version": ">= 1.6.0",
    "required_providers": {
      "aws": {
        "source":  "hashicorp/aws",
        "version": "~> 5.0"
      }
    },
    "backend": {
      "s3": {
        "bucket":         "myapp-terraform-state",
        "key":            "prod/terraform.tfstate",
        "region":         "us-east-1",
        "dynamodb_table": "terraform-locks",
        "encrypt":        true
      }
    }
  },
  "provider": {
    "aws": {
      "region": "us-east-1",
      "default_tags": {
        "tags": { "ManagedBy": "Terraform", "Environment": "prod" }
      }
    }
  },
  "resource": {
    "aws_s3_bucket": {
      "this": {
        "for_each": "${local.buckets}",
        "bucket":   "${each.key}",
        "tags":     "${merge(var.common_tags, { Name = each.key })}"
      }
    },
    "aws_s3_bucket_versioning": {
      "this": {
        "for_each": "${local.versioned_buckets}",
        "bucket":   "${aws_s3_bucket.this[each.key].id}",
        "versioning_configuration": {
          "status": "Enabled"
        }
      }
    },
    "aws_s3_bucket_public_access_block": {
      "this": {
        "for_each":               "${local.buckets}",
        "bucket":                 "${aws_s3_bucket.this[each.key].id}",
        "block_public_acls":       true,
        "block_public_policy":     true,
        "ignore_public_acls":      true,
        "restrict_public_buckets": true
      }
    }
  },
  "locals": {
    "buckets": {
      "myapp-assets":   { "versioning": true },
      "myapp-logs":     { "versioning": false },
      "myapp-backups":  { "versioning": true }
    },
    "versioned_buckets": "${{ for k, v in local.buckets : k => v if v.versioning }}"
  }
}

Equivalent HCL (main.tf) — For Reference

// The .tf.json above is equivalent to this HCL
// HCL is easier to read and write by hand; .tf.json is easier to generate programmatically

locals {
  buckets = {
    "myapp-assets"  = { versioning = true  }
    "myapp-logs"    = { versioning = false }
    "myapp-backups" = { versioning = true  }
  }
  versioned_buckets = { for k, v in local.buckets : k => v if v.versioning }
}

resource "aws_s3_bucket" "this" {
  for_each = local.buckets
  bucket   = each.key
  tags     = merge(var.common_tags, { Name = each.key })
}

resource "aws_s3_bucket_versioning" "this" {
  for_each = local.versioned_buckets
  bucket   = aws_s3_bucket.this[each.key].id
  versioning_configuration { status = "Enabled" }
}

Variables and tfvars: Injecting JSON Config

// variables.tf.json — declare input variables
{
  "variable": {
    "region": {
      "type":        "string",
      "default":     "us-east-1",
      "description": "AWS region to deploy into"
    },
    "common_tags": {
      "type":    "map(string)",
      "default": {}
    },
    "bucket_config": {
      "type": "map(object({ versioning = bool }))",
      "default": {}
    }
  }
}

// terraform.tfvars.json — supply values from your JSON config
{
  "region": "us-east-1",
  "common_tags": {
    "Environment": "prod",
    "Team":        "platform"
  },
  "bucket_config": {
    "myapp-assets":  { "versioning": true },
    "myapp-logs":    { "versioning": false },
    "myapp-backups": { "versioning": true }
  }
}

// The terraform.tfvars.json file is loaded automatically.
// For environment-specific overrides:
terraform apply -var-file="prod.tfvars.json"
terraform apply -var-file="staging.tfvars.json"

Outputs: Export Infrastructure State as JSON

// outputs.tf.json
{
  "output": {
    "bucket_arns": {
      "value":       "${{ for k, b in aws_s3_bucket.this : k => b.arn }}",
      "description": "ARN of each provisioned S3 bucket"
    },
    "bucket_names": {
      "value":       "${values(aws_s3_bucket.this)[*].id}"
    }
  }
}

# After apply, get outputs as JSON (pipe to other tools)
terraform output -json bucket_arns
# → { "myapp-assets": "arn:aws:s3:::myapp-assets", ... }

# Feed output into another system
terraform output -json | jq '.bucket_arns.value' | xargs aws s3 ls

Importing Existing Resources

// If resources already exist (created manually), import them into Terraform state.
// This is common when converting an existing cloud environment to IaC.

# 1. Add the resource block to your configuration
# 2. Import the existing resource by its cloud ID
terraform import 'aws_s3_bucket.this["myapp-assets"]' myapp-assets

# For for_each resources, use the map key in quotes
terraform import 'aws_s3_bucket.this["myapp-logs"]' myapp-logs

# Terraform 1.5+: import block in configuration (no CLI command needed)
# import.tf.json
{
  "import": [
    {
      "to": "${aws_s3_bucket.this[\"myapp-assets\"]}",
      "id": "myapp-assets"
    }
  ]
}
# Run: terraform plan  (shows import plan, no apply needed yet)
# Run: terraform apply (imports and records in state)

Generating .tf.json Programmatically

// Node.js: generate Terraform JSON from a config file
import fs from 'fs';

const config = JSON.parse(fs.readFileSync('infra-config.json', 'utf8'));

const buckets: Record<string, { versioning: boolean }> = {};
for (const bucket of config.s3_buckets) {
  buckets[bucket.name] = { versioning: bucket.versioning };
}

const tfJson = {
  terraform: {
    required_providers: {
      aws: { source: "hashicorp/aws", version: "~> 5.0" }
    }
  },
  locals: { buckets },
  resource: {
    aws_s3_bucket: {
      this: {
        for_each: "${local.buckets}",
        bucket:   "${each.key}",
        tags:     config.tags
      }
    }
  }
};

fs.writeFileSync('generated.tf.json', JSON.stringify(tfJson, null, 2));
// Run: terraform validate && terraform plan

Best Practices for Production

  • Always use remote state with locking: Local state (terraform.tfstate) is lost when the CI container exits and allows concurrent applies. Use an S3 backend with DynamoDB locking (AWS) or a Terraform Cloud workspace. Remote state also enables state sharing between workspaces via terraform_remote_state data source.
  • Run terraform plan before every apply: The plan shows exactly which resources will be created, modified, or destroyed. Never run terraform apply -auto-approve in production without reviewing the plan. In CI/CD, save the plan as an artifact (-out=plan.tfplan) and apply only the saved plan.
  • Prefer HCL for human-authored configs, .tf.json for machine-generated: HCL supports comments, which are important for documenting why a resource is configured a certain way. Use .tf.json only when generating configs programmatically. Never mix both formats for the same logical resource.
  • Use for_each over count for resource sets: count uses numeric indices — if you remove a bucket from position 1 of a list, Terraform will try to recreate all subsequent buckets. for_each uses stable string keys, so removing one resource only destroys that resource.

FAQ

Q: What's the difference between terraform import and writing a data source?
A: import brings an existing resource under Terraform management — Terraform creates a state entry and future plan commands compare the config against the real resource. A data source reads a resource's attributes for use in other resources without managing it. Use import when Terraform should own the resource lifecycle; use a data source when you just need to reference something Terraform doesn't manage.

Q: How do I handle secrets in Terraform (API keys, passwords)?
A: Never put secrets in .tf or .tf.json files — they end up in the state file in plain text. Use AWS Secrets Manager / Parameter Store as data sources, Vault provider, or environment variables (TF_VAR_db_password). The state file should be encrypted at rest (S3 SSE or Terraform Cloud).

Q: Can I generate Terraform for multiple cloud providers?
A: Yes — .tf.json works with any provider. The structure is the same: { "resource": { "google_storage_bucket": {...} } } for GCP, { "resource": { "azurerm_storage_account": {...} } } for Azure. The challenge is that each provider has different attribute names — a code generator needs to know the provider's resource schema.

Q: When should I use modules vs separate workspaces?
A: Modules encapsulate a group of resources with a reusable interface — use them for repeated patterns (VPC, EKS cluster, microservice deployment). Workspaces (or separate state backends) separate environments — use them when prod and staging need completely independent state, not just different variable values.
