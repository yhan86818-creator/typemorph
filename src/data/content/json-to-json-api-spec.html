JSON to JSON:API Spec: Resource Objects, Relationships, Sparse Fieldsets, and Compound Documents

JSON:API (jsonapi.org) is a specification for structuring REST API responses, not just a naming convention. Converting regular JSON to JSON:API compliance requires understanding four key concepts: resource objects (every entity has a type and id), relationships (links to other resources, separate from attributes), compound documents (sideloading related resources in included to avoid N+1 requests), and sparse fieldsets (client-specified field filtering via ?fields[articles]=title,slug). This guide covers the transformation rules, a Node.js serializer library, and the server-side implementation considerations.

The JSON:API Transformation Rules

// Rule 1: Every entity needs type (plural resource name) and id (string)
// Rule 2: Direct attributes go in "attributes" — NOT id, type, or relationship refs
// Rule 3: Links to other resources go in "relationships"
// Rule 4: Related resources are sideloaded in "included"
// Rule 5: Top-level "data" is a resource object (single) or array (collection)

interface JsonApiResource {
  type:          string;
  id:            string;
  attributes?:   Record<string, unknown>;
  relationships?: Record<string, JsonApiRelationship>;
  links?:        { self?: string; related?: string; };
  meta?:         Record<string, unknown>;
}

interface JsonApiRelationship {
  data:   { type: string; id: string } | Array<{ type: string; id: string }> | null;
  links?: { self?: string; related?: string; };
}

interface JsonApiDocument {
  data:      JsonApiResource | JsonApiResource[];
  included?: JsonApiResource[];
  meta?:     Record<string, unknown>;
  links?:    { self?: string; first?: string; last?: string; prev?: string | null; next?: string | null; };
}

// Transformation function
function toJsonApi(
  entity: Record<string, unknown>,
  type: string,
  relationships: Record<string, { type: string; field: string }> = {},
  includeRelated = true
): JsonApiDocument {
  const attrs: Record<string, unknown> = {};
  const rels:  Record<string, JsonApiRelationship> = {};
  const included: JsonApiResource[] = [];

  for (const [key, value] of Object.entries(entity)) {
    if (key === 'id') continue;

    const relDef = relationships[key];
    if (relDef) {
      if (Array.isArray(value)) {
        // Has-many relationship
        rels[key] = { data: (value as any[]).map(v => ({ type: relDef.type, id: String(v.id) })) };
        if (includeRelated) {
          included.push(...(value as any[]).map(v => ({
            type: relDef.type, id: String(v.id),
            attributes: Object.fromEntries(Object.entries(v).filter(([k]) => k !== 'id')),
          })));
        }
      } else if (value && typeof value === 'object') {
        // Belongs-to relationship
        const rel = value as Record<string, unknown>;
        rels[key] = { data: { type: relDef.type, id: String(rel.id) } };
        if (includeRelated) {
          included.push({
            type: relDef.type, id: String(rel.id),
            attributes: Object.fromEntries(Object.entries(rel).filter(([k]) => k !== 'id')),
          });
        }
      }
    } else {
      attrs[key] = value;
    }
  }

  return {
    data: { type, id: String(entity.id), attributes: attrs, relationships: rels },
    included: included.length > 0 ? included : undefined,
  };
}

// Generating JSON:API errors from Zod validation errors:
import { z } from 'zod';

function zodToJsonApiErrors(zodError: z.ZodError): { errors: object[] } {
  return {
    errors: zodError.errors.map(err => ({
      status: '422',
      code:   'VALIDATION_FAILED',
      title:  'Validation Error',
      detail: err.message,
      source: { pointer: '/data/attributes/' + err.path.join('/') },
    })),
  };
}

Best Practices for Production

  • Deduplicate included resources: If two articles share the same author, include that author resource only once in the included array. Use a Set tracking type:id keys to prevent duplicates. Most serializer libraries handle this automatically — if building manually, track included resources in a Map<string, JsonApiResource>.
  • Use a serializer library rather than building it manually: The jsonapi-serializer (Node.js) or fractal (PHP) libraries handle the spec requirements correctly — including relationship linkage, compound document deduplication, sparse fieldsets, and links. Manual serialization usually misses edge cases like null relationships or circular includes.
  • Always send Content-Type: application/vnd.api+json: The spec requires this content type for all JSON:API requests and responses. A client that sends application/json should receive a 415 Unsupported Media Type response. Many JSON:API client libraries (like ember-data, jsonapi-resources) require the correct content type.
  • Don't include related resources by default — require explicit include: Automatically sideloading all relationships creates bloated responses for clients that don't need the data. Support the include query parameter (GET /articles?include=author,tags) and only sideload when requested. This aligns with the JSON:API spec and improves response performance.

FAQ

Q: When should I use JSON:API vs a plain REST JSON API?
A: JSON:API adds the most value when you have complex relational data where clients frequently need related resources together (avoiding N+1 requests), when you want to standardize response formats across multiple teams, or when using frontend frameworks like Ember.js that have first-class JSON:API support. For simple CRUD APIs or when speed of development matters more than standardization, plain REST JSON is simpler.

Q: How does JSON:API compare to GraphQL for reducing over/under fetching?
A: GraphQL lets clients specify the exact data shape per query — more flexible than JSON:API's sparse fieldsets and includes. JSON:API requires the server to predefine which relationships and fields can be requested. GraphQL is better for highly heterogeneous client needs; JSON:API is better for REST-based teams that want a standardized structure without a query language layer.

Q: How do I handle many-to-many relationships with attributes?
A: Model the join table as its own resource. Instead of a direct articles → tags relationship, create a taggings resource with type: "taggings" that has relationships.article and relationships.tag, plus attributes like addedAt. This is more verbose but correctly represents the join record as a first-class resource.
